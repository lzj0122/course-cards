一、连接与报文基础

01TCP 与 UDP 的区别

TCP 面向连接、提供可靠交付、面向字节流、支持全双工通信，首部最小 20 字节；UDP 无连接、尽最大努力交付（不可靠）、面向数据报、支持一对一/一对多/多对多通信，首部固定 8 字节。TCP 适用于文件传输、网页浏览等要求可靠的场景；UDP 适用于视频直播、DNS 查询、在线游戏等实时性优先的场景。

02TCP / UDP 首部长度

TCP 首部固定部分 20 字节，含选项时最长 60 字节（数据偏移字段以 4 字节为单位，最大 15）；UDP 首部固定 8 字节：源端口、目的端口、长度、校验和各 2 字节。

03三次握手的过程与原因

过程：① 客户端发送 SYN=1、seq=x；② 服务端回复 SYN=1、ACK=1、seq=y、ack=x+1；③ 客户端发送 ACK=1、seq=x+1、ack=y+1。原因：同步双方初始序号 ISN 并确认双方收发能力；若只有两次握手，已失效的连接请求报文突然到达服务端时会错误建立连接，造成资源浪费。

04四次挥手的过程与原因

过程：① 主动方发 FIN=1、seq=u；② 被动方回 ACK、ack=u+1（此时主动方→被动方方向关闭，连接处于半关闭状态）；③ 被动方数据发完后发 FIN=1、seq=w；④ 主动方回 ACK、ack=w+1，进入 TIME_WAIT。原因：TCP 全双工，两个方向必须各自独立关闭；被动方的 ACK 与 FIN 通常不能合并（中间可能还有数据要发送），因此是四次而非三次。

05TIME_WAIT 与 2MSL

主动关闭方在发出最后一个 ACK 后进入 TIME_WAIT，持续 2MSL（最长报文段寿命的两倍，Linux 常见 60 秒）。作用：① 若最后一个 ACK 丢失，被动方会重传 FIN，TIME_WAIT 保证能重发 ACK，使连接正常关闭；② 让本连接产生的所有旧报文在网络中消散，避免污染相同四元组的新连接。

06序号与确认号

TCP 把数据看作字节流，序号 seq 是本报文段第一个数据字节的编号；确认号 ack 表示期望收到对方下一个报文段的第一个数据字节序号，即 ack=N 表示 N−1 为止的字节已全部正确收到。ACK 标志位为 1 时确认号字段才有效，连接建立后所有报文 ACK 均置 1。

二、窗口与流量控制

07滑动窗口与流量控制

接收方在 ACK 报文中通告接收窗口 rwnd，发送方的发送窗口不得超过 rwnd，从而让发送速率与接收方处理能力匹配。窗口为 0 时发送方停止发送数据，并启动持续计时器，定期发送窗口探测报文防止死锁。流量控制是端到端机制，抑制的是发送方。

08流量控制与拥塞控制的区别

流量控制防止接收方来不及接收（端到端，依据 rwnd）；拥塞控制防止过多数据注入网络导致路由器/链路过载（全局性，依据拥塞窗口 cwnd）。实际发送窗口 = min(rwnd, cwnd)。

三、拥塞控制四算法

09慢启动（Slow Start）

连接开始时 cwnd=1 MSS，每收到一个对新报文段的确认 cwnd 加 1 MSS，效果是每经过一个 RTT，cwnd 翻倍（指数增长）。当 cwnd 达到慢启动门限 ssthresh 时转入拥塞避免。"慢"是相对一开始就注入大量数据而言，并非增长慢。

10拥塞避免（Congestion Avoidance）

cwnd ≥ ssthresh 后进入拥塞避免：加性增，每经过一个 RTT，cwnd 增加 1 MSS（线性增长），使网络缓慢逼近拥塞。一旦出现超时：ssthresh 设为当前 cwnd 的一半，cwnd 重置为 1 MSS，重新执行慢启动。

11快重传（Fast Retransmit）

接收方每收到一个失序报文段就立即发送对最后一个按序到达字节的重复确认；发送方一连收到 3 个重复 ACK 就立即重传对方尚未收到的报文段，而不必等待重传计时器超时，可显著降低恢复时延。

12快恢复（Fast Recovery）

与快重传配合：收到 3 个重复 ACK 时，ssthresh 与 cwnd 均设为当前 cwnd 的一半（乘性减），然后直接执行拥塞避免（加性增），而不回到慢启动。理由：能收到重复 ACK 说明网络仍有一定交付能力，只是个别报文丢失。注意区分：超时 → 慢启动重来；3 个重复 ACK → 快恢复。

13重传计时器与 RTO

发送方为每个已发送未确认的报文段维护重传计时器，超时时间 RTO 基于往返时间 RTT 的加权平均（SRTT）与偏差（RTTVAR）动态估算：RTO = SRTT + 4×RTTVAR。RTO 过小导致不必要重传，过大导致空闲等待。重传报文不用于更新 RTT 样本（Karn 算法），并对 RTO 做指数退避。

四、工程与应用

14TCP 粘包 / 拆包

成因：TCP 面向字节流、不保留应用层报文边界；发送方 Nagle 算法合并小包、接收方缓冲区读取不及时都会造成多个应用报文粘连（粘包）或一个报文被拆分读取（拆包）。UDP 面向数据报，天然有边界，不存在粘包。解决方案：① 定长消息；② 特殊分隔符（如 HTTP 的 \r\n\r\n）；③ 消息头携带长度字段（最常用，如 Length + Body 协议）。

15常见应用层端口号

FTP 21（控制）/ 20（数据）、SSH 22、Telnet 23、SMTP 25、DNS 53（查询用 UDP，区域传送用 TCP）、HTTP 80、HTTPS 443。端口号 16 位：0–1023 熟知端口，1024–49151 登记端口，49152–65535 客户端临时端口。

16TCP 可靠传输机制小结

TCP 的可靠性由一组机制共同保证：校验和（丢弃损坏报文）、序号与确认（去重、按序交付）、重传（超时重传 + 快重传）、滑动窗口（流量控制）、拥塞控制（慢启动/拥塞避免/快重传/快恢复）。答题时按"检错—排序—补漏—限速—防堵"五个层次展开。
